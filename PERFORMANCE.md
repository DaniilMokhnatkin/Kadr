# Плавность ввода и кадров — 30 октября 2026

## Исправление остановки анимаций без мыши

`draw_ready` снимал запрос следующего кадра, как только затихала панель. Пунктир,
сканирование/проявление цензуры, подглядывание и закрытие оверлея в проверку не входили.
Цикл засыпал до следующего события мыши. Теперь каждый такой эффект сохраняет ожидание
DXGI своей поверхности. Учитывается и подсвеченное окно до окончательного выделения.
Завершившийся эффект освобождает ожидание; не затронутый монитор не перерисовывается
на частоте соседнего. Нет постоянного 1-мс таймера при доступном waitable swap chain.

Проявление длится 640 мс с quintic smoothstep (нулевая скорость/ускорение на краях),
каскад ограничен 450 мс. Даже для 256 областей весь вход с подсветкой короче 2 с.
Тяжёлая подготовка слоя остаётся в фоне до начала часов анимации.

Проверено: 240 последовательных запросов кадров без ввода, затем переход в простой;
40 Present на настоящем DXGI в offscreen DWM-cloaked окне без мыши/смены фокуса;
проверки конечного эффекта и независимости мониторов. Это проверка готовности кадров,
не измерение физического scanout. Для desktop composition используется FLIP_SEQUENTIAL,
согласно [контракту Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgifactory2-createswapchainforcomposition).

Повторный offscreen GPU-completion замер 2560×1440, 100 областей, 330 прогретых кадров:
подготовка 128.186 мс, upload 0.957 мс, холодный первый кадр 18.635 мс;
p50 1.881 мс, p95 3.248 мс, max 4.196 мс. D2D recording p95 1.448 мс,
EndDraw/Flush p95 1.064 мс, ожидание GPU p95 1.796 мс. Все 330 уложились в бюджет
5.882 мс. Предыдущий прогон на этом же ПК дал около 16 мс: внешняя нагрузка/состояние
драйвера остаются переменными, поэтому эти результаты не гарантируют 170 FPS в работе.

## NVIDIA App: исключение только для Kadr

Установщик содержит небольшой NVAPI DRS helper, загружающий nvapi64.dll из System32.
Он создаёт отдельный профиль `Kadr screenshot utility` для `kadr.exe`, задаёт
`0x809D5F60=0x10000000` (disable NVIDIA App statistics) и выключает Ansel только в нём,
сохраняет и перечитывает значения. [Источник флагов](https://github.com/Orbmu2k/nvidiaProfileInspector/blob/master/nvidiaProfileInspector/CustomSettingNames.xml),
[ABI NVIDIA](https://github.com/NVIDIA/nvapi/blob/main/nvapi.h).
Чужой/общий/predefined профиль не меняется; глобальные настройки не затрагиваются.
Нет NVIDIA — шаг пропускается; ошибка helper не мешает установке и видна в предупреждении.

Windows PowerShell 5.1: компиляция C#, размеры ABI, запрет чужого/общего профиля и настоящий
read-only вызов драйвера проверены. Сам helper записи автоматически не запускался:
он выполняется при установке пользователем. Исчезновение уведомления NVIDIA после
применения профиля ещё требует проверки в обычной работе; флаг зависит от драйвера.

## Предыдущие исправления ввода и отрисовки

Сообщённый дефект: прицел запаздывает, кисть выглядит рваной. До изменения:

- on_pointer использовал GetCursorPos вместо координат WM_MOUSEMOVE. Во время задержки
  разные события подменялись одной уже более новой позицией. Промежуточные точки не восстанавливались.
- В каждом обработчике движения синхронно перерисовывались все мониторы и вызывался Present.
  Отсутствие ожидания SyncInterval не означает, что Present никогда не блокирует поток ввода.
- Проверка попадания в тулбар заново создавала все DirectWrite layouts: 0.279–0.296 мс на вызов.
- Области размытия считались заново для каждой поверхности, даже вне её экрана.

Исправления:

1. Координаты события переводятся из client в screen, отрицательные значения сохраняются.
   GetMouseMovePointsEx возвращает доступные до 64 промежуточных точек. Они проигрываются по времени
   между mouse-down и текущим событием, без повторения старой части штриха; ошибка API оставляет конечную точку.
2. Движения меняют модель и помечают кадр грязным. Очереди устаревших кадров нет.
   MsgWaitForMultipleObjectsEx обрабатывает ввод, пока DXGI не даст готовность конкретного монитора.
   Для него Present(1, DO_NOT_WAIT); WAS_STILL_DRAWING сохраняет последний кадр для повтора,
   а не блокирует мышь и не теряет сигнал готовности. Медленный монитор не является барьером для быстрого.
   На драйверах без waitable swap chain предусмотрен неблокирующий повтор с коротким timeout.
3. Геометрия и layouts панели кэшируются по размеру, выделению и параметрам. Тот же замер — 0.001–0.002 мс.
   Движение над неизменённым готовым выделением не вызывает перерисовку.
4. CPU-композит размытия общий для поверхностей, GPU-копия своя у каждого адаптера.
   Ключ включает сами фигуры, crop и идентичность живых Arc кадров. Кэш очищается при закрытии сессии.
   Вне пересечения crop с экраном аннотации не вычисляются. Алгоритм размытия и его пиксели сохранены.

## Замер и отвергнутые попытки

`kadr.exe --interaction-bench result.txt` создаёт синтетический кадр 1920×1080, выполняет 80 шагов
для пера и кисти размытия (первые 10 исключены) и 400 hit-tests панели. Это CPU/GPU submission,
без окна, курсора, реальной развёртки и измерения input-to-photon. Сборка release, одинаковые данные.

| Попытка | Наблюдение | Решение |
|---|---|---|
| Кэш hit-test/layout | 0.28–0.30 → 0.001–0.002 мс, три прогона | оставлен |
| Локальная арифметика blur/mask | p50 5.56–5.89 → 5.28–5.53 мс, p95 нестабилен | откачена вместе с экспериментом интерполяции |
| Горизонтальная прединтерполяция сетки | p50 5.88–6.76 мс, p95 8.62–10.93 мс | откачена |
| Общий CPU blur для мониторов | проверяется повторное использование одного Arc и сброс при замене кадров | оставлен, нет обещания ускорить сам blur на одном экране |
| Ожидание кадров по отдельным мониторам | тест 1000 запросов; настоящее GPU-событие и Present в скрытом окне | оставлено; физический FPS этим тестом не измерен |

Перо само по себе было быстрым (около 0.08–0.09 мс offscreen), поэтому геометрия не заменялась
произвольным сглаживанием. Тест потери изгиба специально ломался мутацией временного фильтра и падал.

Проверки: tools/check.ps1, Clippy -D warnings, release; реальная развёртка и ощущение на 170/240 Гц
остаются проверкой новой сборки на экране. PNG и скрытые окна не выдаются за такое измерение.
Итоговый прогон: 84 теста. Контрольный экспорт synthetic scene старой и новой версии совпал пиксель в пиксель.

Основания API: [история мыши](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmousemovepointsex),
[DXGI frame latency](https://learn.microsoft.com/en-us/windows/uwp/gaming/reduce-latency-with-dxgi-1-3-swap-chains),
[DO_NOT_WAIT](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-present).


## Цензура: подготовка перед анимацией (2026-10-30)

OCR получает изображение в отдельном offscreen-контексте рабочего потока. После распознавания
в фоне готовится полный CPU-слой цензуры, включая композицию участков. Готовые пиксели загружаются
в поверхности до старта часов анимации; проход луча и проявление начинаются после подготовки.
Результат отбрасывается, если за время работы изменились кадры, выделение или аннотации.

PaddleOCR использует один вычислительный поток без spin-wait в обоих сеансах. Число потоков
размытия ограничено двумя, прогрев не создаёт дополнительный параллельный пул.
Каскад для 256 областей ограничен длительностью менее двух секунд вместо примерно 15 секунд.

Воспроизводимый синтетический замер: `KADR_BENCH_CENSOR=1` и
`kadr.exe --motion-bench target/censor-final.txt` (release, без uiAccess для запуска вне Program Files).
Кадр 2560×1440, 100 областей с одновременной подсветкой и сканирующим лучом:
подготовка CPU 77.659 мс, загрузка GPU до анимации 2.106 мс;
кадры CPU + завершение GPU p50 1.496 мс, p95 1.961 мс, max 2.424 мс.
Холодный первый кадр всей сцены 16.246 мс учтён отдельно; первые 10 кадров исключены из перцентилей.
Это offscreen-замер рендера, без OCR под нагрузкой и без измерения реальной развёртки монитора.
Плавность установленной версии на настоящем выделении остаётся отдельной проверкой.


## Продолжение: фильтр и офлайн-перевод (2026-10-30)

Кэш patches ограничен 64 МиБ; цельный слой переиспользуется до загрузки в GPU. Композиция
размытий использует маску, поэтому прозрачные края следующего участка не восстанавливают
уже скрытые пиксели предыдущего. Light/Hard используют общий OCR-кэш неизменённого снимка;
Full ищет области текста без чтения каждой буквы, на больших областях — перекрывающимися
тайлами исходного разрешения, затем проверяет получившийся слой повторно. При переполнении
256 фигур оставшиеся области объединяются, а не молча отбрасываются.

Последний offscreen-замер 100 областей 2560×1440: подготовка 104.581 мс, GPU upload 1.931 мс,
p50 кадра 1.473 мс, p95 1.834 мс, max 2.450 мс; холодный первый кадр всей сцены 16.147 мс.
OCR не входит в этот рендер-бенчмарк. Настоящий детектор 3 строк EN/RU: 406 мс с загрузкой
модели и 115 мс прогретый (debug); не обобщать эти числа на большой снимок чата.

Офлайн-перевод вынесен в постоянный скрытый процесс с приоритетом below normal и двумя
вычислительными потоками. Реальные EN→RU и RU→EN вместе с загрузкой двух моделей прошли
за 0.87 с в интеграционном тесте; это одна короткая пара фраз, не гарантия latency любого текста.
